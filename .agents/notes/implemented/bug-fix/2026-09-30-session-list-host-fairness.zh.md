# Agent Note: 按时间片执行 Session 列表工作

Status: implemented

[English](2026-09-30-session-list-host-fairness.md) | 中文

## 问题

较大的缓存投影状态会在组装 Session 列表时独占 Host。每行都让出可以避免整批停顿，却会在包含大量低开销行的列表上增加数千次事件循环往返。行数本身不是合适的调度预算。

## 决策

[ApiSessionList](../../../../packages/api/session-controller/src/list.ts) 对分类和摘要生成共享一个单调时钟截止时间。仅当经过的工作时间耗尽配置的 `listWorkSliceMs` 时才让出，并在等待结束后建立新的截止时间。这个可选部署设置默认为 16 毫秒，要求正整数。小列表没有强制的最后一次让出，也不经过空操作异步 helper。每行、每次让出之后以及返回前检查取消；不会返回部分列表。

每行仍同步计算。live 行先于已进入队列的 cold 行，随后按活动时间稳定排序；列表不承诺跨 Session 的原子 cut。接入前已经排入队列的冷行仍是缓存行，Client 变更重放与 [cached/sequenced 优先级](../architecture/2026-09-19-projection-cache-listing-identity-and-cached-rows.zh.md)协调较新的 live 状态。不省略任何投影数据或校验。

## 验证范围

[受控时钟测试](../../../../packages/api/session-controller/tests/list-scheduling.host.spec.ts)验证经过工作的预算、让出后的截止时间重置、稳定并列排序和取消。16 ms 默认值可配置；这些测试验证调度行为，不保证吞吐量或浏览器渲染改善。本分支不包含上游的投影列表基准及其 CI 性能测试。

## 考虑过的替代方案

**无条件逐行让出。** 它尽量缩短单次排队等待，却对每个低开销行都收取一次事件循环往返成本。这项调度成本随低开销行的数量增长；固定行数同样忽略了行成本差异。

**更大或更小的时间片。** 更小的时间片缩短排队等待，但增加调度成本。更大的时间片减少切换，却延长其他 Host 工作的等待。配置显式提供这一取舍，不改变行语义。

**缓存解码状态或 wire view。** 解码状态复用会为每份存储行保留另一份对象图，并改变 schema 执行的所有权。wire view 可能依赖当前运行状态。调度不需要这两类缓存，且保留全部 schema 校验和动态视图。

## 后果

[受控时钟测试](../../../../packages/api/session-controller/tests/list-scheduling.host.spec.ts)要求低开销行保持在同一同步时间片内，由预算耗尽和等待后重置决定让出，并在无需让出时也能响应取消。测试还保留了稳定并列排序和接入、移除、状态变更的交错行为。

单行、提供方枚举、GC、最终排序和序列化都可能超出目标。并发列表和操作系统调度也会影响延迟。预算不是全局硬上限，调度策略也不保证改善浏览器绘制或模型、网络延迟。
