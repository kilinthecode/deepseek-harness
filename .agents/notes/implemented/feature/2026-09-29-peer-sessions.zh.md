# Agent Note: Peer sessions over one shared Harness home

Status: implemented

[English](2026-09-29-peer-sessions.md) | 中文

## Problem

在同一个仓库中工作的顶层会话无法互相触达。`ctx.agentTeams` 只协调一个 Lead Session 拥有的 teammate，而[相邻智能体 steer 决策](../architecture/2026-08-27-adjacent-agent-steer-messaging.zh.md)只覆盖同一个进程内活跃的智能体；两者都不跨越进程边界：同一个检出目录中的两个 Harness 进程——也就是一个人开两个终端这种最常见的情形——既无法发现彼此，也无法提问，更无法得知某个对等会话进入了空闲。

会话日志属于持有该会话的进程。[跨进程会话写入租约](2026-08-31-cross-process-session-write-lease.zh.md)让第二个写入方成为错误而不是竞争，因此即使发送方想投递进另一个进程的会话也做不到。

## Decision

`@deepseek-ai/dsh-experimental-peer-sessions` 负责 `ctx.peers`：发现、消息投递、空闲订阅，以及支撑它们的持久文件。对等会话是同一个 Harness home 下另一个顶层会话，其仓库键与调用方相同；该键来自 `peerRepoKey`，存在记录是 `$DSH_HOME/peers/presence/` 下每个会话一个文件。`@deepseek-ai/dsh-experimental-tool-peer-sessions` 负责三个模型工具及其框架，[`dsh-experimental-peer-sessions-profile`](../../../../packages/experimental/peer-sessions-profile/README.zh.md) bundle 挂载这两个包，随附组合则不挂载它。[对等会话子系统页](../../../../docs/subsystems/peer-sessions.zh.md)承载持久与客户端可见形式。

**Harness home 下的文件信箱，只由把目标作为实时会话持有的进程排空。** `send` 把一个信封提交进目标的分片，除非本进程持有目标，否则返回 `queued`；持有进程排空该分片、重新应用对等判定与仓库检查，并发出 steer。home 目录是两个互不相关的进程本来就共享的那样东西，因此协同不需要共同的父进程、不需要监听 socket，也不需要注册步骤，消息还能比在投递前退出的发送方活得更久。只在会话存活的位置排空才能保持单写者所有权完整：信封文件只是队列条目，绝不是替代日志。

**绝不异地恢复另一个进程的会话。** 不持有目标的进程绝不写打开它的日志、不向其追加任何持久行，也不为它启动轮次。排队中的信封只有经由接收进程自身的 resume 路径才会被投递，这既让队列在重启后仍然有效，也没有违反写入租约。

**deferred 是时序，不是审批。** `peerInbound: 'deferred'` 在目标空闲期间暂存消息，而不接纳一个轮次；目标下次运行时消息才被投递。接收方用户绝不会先看到正文，因此该模式不能被当成审阅或同意步骤：它存在的目的是让部署能保持空闲会话空闲，而两种模式携带同一套 harness 框架，声明发送方是另一个 agent 而非用户。

**仅宿主侧的投递投影。** 投递由折叠已记录的 `user/message` 来证明，其 source 携带信封的 `source.messageId`，落在与按对端中继深度、空闲轮次位并列的 `peerDelivery` 投影中。该状态是宿主侧记账，不是持久事件，也不是工具结果字段，因此目标的日志中不含任何对等记录行，也没有任何模型可见 schema 承诺发送方无法核实的投递细节。

**进行中 steer 集合。** 一次排空轮次把它 steer 过的信封 id 记入按目标划分的进行中集合，直到该投递出现在日志中，并发的排空轮次会跳过这些 id。只从日志读取接受状态，会让第二轮重复 steer 一个框架已经拼接但尚未落盘的信封，因此该集合把「尚未被接受」与「尚未被尝试」区分开。

**三次尝试后丢弃。** 每次空闲结算如果没有发现投递已应用、也没有发现信封仍待处理，就消耗一次尝试；第三次尝试删除该信封并记录一条写明 id 与原因的警告。会话拒绝该框架的目标否则会被同一个文件永远唤醒，因此这个上界既保留了崩溃后的一次合理重试，也终止了永久循环。

**按 git common dir 分组，用普通文件读取，不启动 git 子进程。** 同一个检出目录的两个 worktree 属于同一对等分组，因为它们共享 git 引用，而这正是协同真正重要的边界。`peerRepoKey` 直接读取 `.git` 标记——目录，或 gitfile 的 `gitdir` 与可选的 `commondir`——因此发现每个会话只需一次有界的向上查找，在 `git` 缺失或被遮蔽时依然可用，也不会被 hook、配置或恶意 `PATH` 拖慢或破坏。没有可用标记时，键为 `dir:` 加规范目录，使检出目录之外的会话仍可按精确路径触达；`GIT_DIR` 被忽略，因为该键指向持有会话自身目录的仓库。

**收到用户消息时重置中继预算。** 中继深度是整份日志中从每个对等会话记录到的最深中继层级，会超过四跳的发送会被拒绝。只有 source 类型为 `user` 的 `user/message` 会清除已记录的深度：真人重新参与是循环之外还有参与者的唯一信号，而调度、webhook、Team 或对等会话生产者只是机器提示机器，让它们重置预算恰恰会在最需要上限的地方失去上限。

**不加锁。** 信箱写入锁只覆盖一个分片的上限检查与一次写入，此外什么也不覆盖。对等协同只是建议性的，理由与 [Agent Teams note](2026-08-05-agent-teams.zh.md)拒绝把所有权或名字当作文件锁时相同：不查询锁的写入方会无视它，崩溃的所有者会把它留下，而虚假的互斥比明确的警告更危险。跨进程时写入方更加不可观测，因此同一结论只会更强。

**接受判定从 `messageAccepted` 派生，而不是导入。** 对等判定问的是与 Agent Teams 相同的问题——这条消息已经进入历史，还是仍在持久待处理——但用对等信封自己的字段来回答，并给出进行中集合所需的投递 id。从 `packages/experimental/agent-team/src/session-message.ts` 导入 `messageAccepted` 会让两个必须各自演进的实验性领域相互耦合，并给对等包一个为 Team 消息塑造的判定；派生实现让 `source.messageId` 成为两者之间唯一的约定，也让已有的信箱上限有据可查。

## Alternatives considered

**进程内共享注册表，或日志旁的一个 socket。** 拒绝，因为进程内注册表看不到另一个 Harness 进程，而 socket 需要一个监听方，其生命周期、端口与认证都不是 home 目录所能定义的。文件信箱是两个互不相关的进程本来就能遵守的最小约定，而且能挺过被替换而非被重启的进程。

**由发送方进程通过目标自己的调度器投递。** 拒绝，因为写入租约使异地写入方成为错误，而绕过接收进程轮次准入的投递会把持久性与框架搬到错误的进程里。

**为邮件新增持久的 `peer/*` 会话事件。** 拒绝，因为日志会因此携带每个消费方与每个 fork 都能看到的对等记账行，而接受判定还需要一个与既有 `user/message` 并列的事件形状答案。仅宿主侧的投影用 harness 本就写入的行来回答它。

**从 Agent Teams 导入 `messageAccepted`。** 拒绝，理由同上文的耦合。派生判定之所以很小，是因为对等信封携带自己的 id 与版本，这正是排空所需的，而 Team 消息并不提供。

**对 deferred 投递加审批关口。** 拒绝，因为该模式的存在是为了让空闲会话保持空闲，而不是增加同意步骤。关口必须被渲染并在某处得到答复，于是每条对等消息都要等接收方用户回来，这恰恰与要求 deferred 模式的部署相反。

**把对等会话的显示名当作它的身份。** 拒绝，因为名字由发送方会话自选，可能重复也可能更改，因此授权与投递解析比较的是会话 id 与仓库键。只有当一个名字与调用方仓库中恰好一个对等会话匹配时，`to` 才会接受它。

## Testing

`repo.spec.ts` 覆盖目录、gitfile 与回退情形下的仓库键；`presence.spec.ts` 覆盖记录写入、重写与 pid 探测；`mailbox.spec.ts` 覆盖分片布局、版本、上限与写入锁；`projection.spec.ts` 覆盖投递折叠、中继深度与空闲轮次位；`deferred.spec.ts` 覆盖暂存消息及其后续投递；`relay.spec.ts` 覆盖跳数上限与重置；`watches.spec.ts` 覆盖订阅、通知与销毁；`authorize.spec.ts` 与 `framing.spec.ts` 覆盖对等判定与 harness 框架；`tools.spec.ts` 覆盖模型工具的 schema 与结果。`peer.e2e.ts` 启动两个随附的 `dsh` 进程共享一个 Harness home，其中一个位于链接的 worktree，并断言跨接收方重启的消息、框架与日志行。

## Consequences

对等协同是可选启用且基于文件的：挂载该 bundle 的部署无需守护进程、端口或共同父进程即可获得发现与投递，而省略它的部署行为完全不变。代价是 Harness home 下多了一个持久表面，它有自己的上限、保留规则，也没有存活心跳，因此上限与陈旧的存在记录对用户可见，并且被记录在案而不是被隐藏。目标由另一个进程持有时，投递延迟取决于轮询间隔；中继上限则让两个会话之间持续的自主往复在四跳后停止，直到真人开口。
