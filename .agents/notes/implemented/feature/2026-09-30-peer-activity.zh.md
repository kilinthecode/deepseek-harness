# Agent Note: Peer activity sharing between top-level sessions

Status: implemented

[English](2026-09-30-peer-activity.md) | 中文

## Problem

在同一个仓库中编辑的两个顶层会话，可能在互不知情的情况下覆盖对方的工作。文件工具已经阻止了其中一类覆盖：只要文件在会话读取之后发生了变化，无论是谁改的，`FS_STALE_VERSION` 都会拒绝这次文件工具写入。但这个拒绝既没有说明是谁改了文件、为什么改，又是在会话已经尝试写入之后才触发；对于同一仓库另一个 worktree 中的会话，它也无能为力，那类会话的改动要到合并时才会冲突。[对等会话](2026-09-29-peer-sessions.zh.md)工具让会话可以发现并向对等会话发消息，但前提是模型自己先决定调用 `list_peers`；而“改动共享引用之前先这样做”的建议，无法覆盖两个模型同时开始处理同一个文件的那一刻。

用户要求的是无需这种决定的协同：同时工作的会话彼此告知自己正在处理什么、在做什么，以免覆盖彼此的工作。这一切对用户而言是在后台发生的，并且与 Team room 功能相互独立。

## Decision

每个顶层会话发布一条活动记录，`PeerService.activitySnapshot` 把调用方的对等会话渲染为一条上下文消息，`tool-peer-sessions` 在 `agent/pre-step` 追加这条消息。没有新增工具、`SessionEventMap` 成员或 agent loop（智能体循环）改动。模型可见的载体是一条已有的 `user/message`，带有新的限定来源 kind `peer-activity`，由[持久化记录](../../../../docs/persistence-changes/2026-09-30-peer-activity-source.zh.md)予以确认。[子系统页](../../../../docs/subsystems/peer-sessions.zh.md#activity)给出记录、快照与来源的形式。

**第三类文件，而不是新的存在记录版本。** 记录位于 `$DSH_HOME/peers/activity/<sha256(sessionId)>.json`，与存在记录和信件并列。存在记录的 schema 是严格的，因此增加字段会让不含活动功能的构建拒绝一条已变化的记录，并把该会话从 `list_peers` 中丢掉。单独一类文件让混合部署保持可读：每个构建的存在记录都保持有效，只有快照会省略没有活动记录的会话。记录带有自己的 `version`，读取方遇到其他版本的记录只跳过而不删除，因为该构建的会话可能仍然存活。

**在 `agent/pre-step` 注入，并从日志去重。** 监听器沿用 `time-context` 的做法：以 `prepend: true` 注册在 agent 自己的上下文上，等待 `next()`，原样返回被拒绝的决定，并把自己的消息追加在该决定自身的消息之后。因此该轮次自己的提示词仍排在最前，已缓存的系统提示词前缀不受影响，循环也把这条消息作为普通 `user/message` 写入日志，模型读到的一切都能从日志重建。监听器只在本来就要调用模型的步骤询问，所用条件与模型选择监听器相同：空的第一步不产生调用，快照不能凭空制造一次调用。因此快照从不开启轮次，客户端的轮次触发器也就不需要 `peer-activity` 条目。

去重由仅宿主侧使用的 `peerActivity` 投影基于已记录的消息完成（最近一次的文本、最近一次的重叠文本与所列出的对等会话 id），而不是进程内存，所以恢复或分叉出来的会话不会重复它已持有的区块。步骤 1 展示发生变化的区块；之后的步骤只有出现新的重叠，或出现上一个区块没有列出的对等会话时才展示。已完成的压缩（compaction）会清除该投影，因为摘要在请求中取代了先前的消息；失败的压缩则保留它。

**新的对等会话在轮次中途被宣告，尝试写入也算数。** 真实模型检查的两项发现催生了这些规则。在每一组真实配对中，先启动的会话都不知道第二个会话已经开始，所以来源携带 `peerIds`，之后的步骤会列出上一条消息没有列出的对等会话。在唯一一次真实冲突中，文件工具拒绝了第一个会话对第二个会话已写过的文件的陈旧写入，而此后没有出现快照，因为当时只有成功的写入才计数。每个有修改作用的工具调用无论结果如何，都会进入进程内的尝试列表，调用方的重叠集合是其新鲜的成功写入加上这些尝试。记录仍然只携带成功的写入，所以对等会话永远不会得知一次被拒绝的尝试。

**只警告，不提供认领工具。** 快照只警告，不阻止，也没有任何工具让会话认领资源。`fs/write-intent` 与 `fs/edit-intent` 是单槽位决定，已被 `fs-observation-policy` 占用且不调用 `next()`，两个槽位都有主且不委派，因此任何认领都无法拒绝一次写入。认领看板（`claim_resource`、`release_resource` 与 `list_claims`，每个仓库一块看板）只会是无法强制执行的记账，还会增加常驻的提示词 token，而用户要求的是在后台发生的行为。声明意图仍然通过 `send_peer_message`，观察到的意图则是活动记录。`overlap: 'off'` 去掉警告，保留区块。

**后代的写入记在顶层会话名下。** subagent、`origin: 'subagent'` 的 fork 以及 Team 的 teammate 完成了大部分文件写入。服务沿 `parentSession` 穿过本进程的存活 agent，最多走后代 header 所记录的 `delegationDepth` 步，到达第一个发布记录的 agent，并把路径记在那里。当这条链离开本进程时，什么也不记录，因为本进程无法写入祖先的记录。后代的 todo 列表与标题永远不会影响根会话的记录，后代自己也不发布记录：每次记录写入都会检查该记录的所有者是存活的顶层对等会话。

**`doing` 取自进行中的 todo 条目。** 记录携带会话自己最新的 `todo_write` 列表中第一个 `in_progress` 条目，截断为 120 个字符。发布用户的请求、计划或目标被否决，因为那会把一个会话的提示词文本带进另一个提供方的模型。todo 条目是模型自己对“此刻在做什么”的陈述，且 `todo/write` 事件本来就写入日志，所以记录不需要新的信号。模型更新列表较晚时，`doing` 会滞后：在一组真实配对中，会话已经写完文件，区块仍然写着第一个条目。

**路径相对于检出根目录生成键。** `rel:` 键相对于 `peerCheckout` 用与 `peerRepoKey` 相同的查找找到的检出根目录，而不是相对于工作目录。否则，在 `<worktree>/packages/x` 中启动的会话会记录 `rel:a.ts`，永远无法与根在 worktree 顶层的对等会话对上。同一仓库的两个 worktree 比较同一个键，根目录之外的路径为 `abs:`。根目录还决定 `checkout` 标签：`shared` 表示可以直接覆盖调用方工作树的对等会话，目录名表示只可能在合并时冲突的对等会话。

**提示词中的共享检出目录 git 指导。** `peer:coordination` 告诉与对等会话共享检出目录的会话：不要丢弃、stash、reset、checkout 或清理工作树，也不要暂存全部内容，因为这些命令会移除或提交对等会话未提交的工作。陈旧版本检查看不到通过 Bash 运行的 git 命令，所以这段指导是该情形下唯一的保护。它只是文字，不约束任何人；文件工具仍是唯一的强制手段。

**对等会话的文本经过编码，且框架在前。** 对等会话的标题、`doing` 行与路径都是另一个模型选定的文字。区块之前有一行固定的区块头，说明它是关于其他 agent 的数据，不授予任何权限，也不提出任何请求。每个由对等会话选定的字符串都经过 JSON 编码，`<` 写作 `\u003c`，区块内与重叠语句中一致，因此拼出结束标签的标题也无法结束区块。

**读取失败不会让步骤失败。** `activitySnapshot` 运行在每个符合条件的 agent 的 pre-step 内。Harness home 的读取失败，例如 `peers/activity` 的位置上是一个文件，会记一条警告并且不产生快照，因为对等活动只是建议性的。

**随附的取值。** `activityTtlMs` 为 30 分钟，因为对等会话未提交的编辑在 15 分钟之后仍然相关。`maxActivityFiles` 为 12，因为 6 个会漏掉普通多文件改动中的重叠。`maxActivityPeers` 为 4，`maxActivityBytes` 为 4096，`overlap` 为 `warn`。每一项都是经过校验的配置字段，取值无效时的加载错误会指明该字段。

**不改 UI。** 客户端把每条已记录的上下文消息渲染为一行默认折叠的记录，标题为“Context injection”，其后是生产者的标签；没有特殊处理的生产者，标签就是持久的 kind，`time-context` 的记录已经是这样显示的。因此 `peer-activity` 记录显示为“Context injection · peer-activity”。本地化生产者标签会改变每个生产者的标注方式，所以等 Portal 反馈这个标签读起来不好时再处理。

## Alternatives considered

**把活动字段放进存在记录。** 拒绝，理由同上文的混合部署问题。

**发布用户的请求、计划或目标。** 拒绝：它会在提供方之间传递提示词文本，没有上限，也没有可读取的稳定导出投影。只有在具备这样的投影、并就是否跨会话传递提示词做出决定之后，才重新考虑。

**认领看板。** 拒绝，理由是它属于无法强制执行的记账，见上文。

**在重叠时阻止写入。** 推迟，直到文件工具会去查询一个可以拒绝写入的写入授权服务；目前两个 intent 槽位都有主且不委派。

**为重叠增加 `tools/post-execute` 上的第二次折叠。** 拒绝：它的上下文同样落在下一个请求里，所以额外的挂钩、来源 kind 和逐轮次限流，相比一次 `agent/pre-step` 注入并不会换来模型可见的延迟改善。

**通过 `steer` 或信箱在重叠时唤醒对等会话。** 拒绝：本会话的路径到达后，对等会话的渲染就会变化，所以对等会话在它自己的下一个步骤就会得知。唤醒会消耗该对等会话的轮次预算与中继深度。

**每轮一次的闩锁，或无条件的步骤 1 注入。** 拒绝，转而采用基于持久投影的内容去重（两种设计都需要它来保证恢复安全），再配合之后步骤的重叠与新对等会话规则。

**分支字段。** 放弃：没有消费方能把它用作触发条件，每次发布都要多读一次 gitfile，而 git 拒绝同一分支在两个 worktree 中同时检出，因此这个信号大多是噪声。

**可配置的修改类工具名列表。** 拒绝：哪些工具名会修改文件是 `workspace-changes` 已拥有的固定规则。复制一份会产生偏差并使 `pnpm run duplication` 失败，所以由 `@deepseek-ai/dsh-workspace-changes` 导出 `mutationPath`，本服务复用它。可配置的列表则会对规则不认识的名字悄悄什么也不发布。

## Testing

`activity.spec.ts` 覆盖记录的创建与删除、成功与失败的写入、跨 worktree 与嵌套目录的检出根目录键、后代归属及其限制、`doing`、文件数量上限、已死进程与其他版本的记录，以及每一种配置拒绝。`activity-snapshot.spec.ts` 覆盖列出过滤、排序、对等会话数量上限、检出目录标签、逐字渲染、对恶意名称的编码、包含尝试写入与新鲜度的重叠，以及每一步截断。`activity-dedupe.spec.ts` 覆盖步骤 1 与之后步骤的规则、新对等会话、压缩后的重置以及恢复。`activity-queue.spec.ts` 覆盖随发布队列执行的删除，以及已销毁的根会话不留记录。`tools.spec.ts` 覆盖注入：正确的 agent 会话里恰有一条消息，subagent 没有，agent 销毁或插件卸载之后没有，被拒绝或被中止的步骤保持原样，被清空的第一步与被清空的续接步骤保持原样，携带新重叠的续接步骤则有消息。`peer.e2e.ts` 拉起两个正式的 `dsh` 进程，一个在主检出目录，一个在链接的 worktree，两者通过真实文件工具写入同一个相对于仓库的路径，并断言各自的下一轮次都记录一条指明对方与重叠的 `peer-activity` 消息。无需密钥的快照 `snapshots/session/peer-activity/` 记录模型可见的区块头、区块与重叠语句。

## Real-model check

两个使用不同模型的 headless 会话在同一个共享 git 检出目录中运行，共用一个临时 Harness home，并启用该 bundle。三组真实配对使用 MiMo v2.6 pro 与 flash，其中 flash 会话两次使用 `high` 推理、一次关闭推理。另有两次运行把一个真实会话与一条脚本化的对等会话记录配对，该记录在存活 pid 下发布，schema 与真实记录相同，用来强制走到重叠路径。任务是给一个文件的每个导出加 JSDoc，以及重命名一个函数及其调用处。

- 在三组真实配对中，后启动的会话都在步骤 1 收到了对等会话的区块（一条 380 到 461 个字符的消息）。先启动的会话一条也没有收到，这催生了新对等会话规则。
- 没有一组真实配对出现重叠段落，因为两个会话从未在两个进程都存活时同时写过有争议的文件。其中两组里，第二个会话等第一个会话发出放行消息，并在第一个会话退出之后才写；第三组里，第一个会话早先的写入被拒绝，它第一次成功的写入发生在第二个会话退出之后。
- 脚本化对等会话的运行在轮次中途产生了重叠段落（753 与 759 个字符）。两个模型随后都在一到两个步骤内重新读取了有争议的文件，并且没有再写它。
- 在第三组配对中，文件工具拒绝了第一个会话在第二个会话重命名之后的陈旧整文件写入，此后没有出现快照。这一发现催生了尝试写入规则。第一个会话随后重新读取该文件并保留了重命名。
- 没有模型运行 git 命令，五次运行中两处改动都保留了下来。五次运行中有四次，看到对等会话区块的会话在写入之前先给对等会话发了消息，这缩小了出现重叠的窗口；例外是第三组配对中关闭推理的 flash 运行。
- 步骤 1 的区块大约花费 95 到 155 个 token，带重叠语句的消息为 190 到 250 个 token，均按每 token 3 到 4 个字符由字符数估算。

每种配置只有一到两个样本，所以模型的反应只是观察，不是比率。日志不含提供方的用量数据，逐步骤的文件读取也没有测量。

## Deferred

每一项都在等待自己的触发条件。强制阻止等待文件工具查询、且可以拒绝写入的写入授权服务。针对分支或共享 git 引用的重叠，等待 `repo.ts` 中经过验证的引用读取器（它目前只读取 `.git` 标记）。在活动变化时唤醒对等会话，等待显式的用户设置，因为它会消耗该对等会话的轮次预算。Bash、PTC 与其他非文件工具的写入覆盖，等待这些工具在运行之后报告它们修改过的路径。本地化的生产者标签等待 Portal 反馈。不同仓库之间对同一个 Harness home 文件的争用，等待比仓库键更宽的分组。

## Consequences

对每个挂载该 bundle 的会话，活动共享都是自动的：不需要工具调用，除该 bundle 外无需任何配置，也不需要用户安排任何事。它的成本是有界的。符合条件的会话在每个调用模型的步骤读取活动目录，一个发生变化的快照只增加一次 60 到 250 个 token 且绝不超过 `maxActivityBytes`，`peer:coordination` 段落中的两段活动说明约有 200 个词，每个带该 bundle 的会话无论有没有对等会话都要为此付出。

它换来的东西同样有界。信息只覆盖文件工具的写入，可能落后一步，并且在第二个写入方写入之后才到达它，而不是之前，因此它能警告，无法预防。陈旧版本检查仍是唯一的强制手段，通过 Bash 运行的 git 命令只有提示词文字覆盖。独立的文件类别意味着已退出进程的记录会留在磁盘上，直到有读取方探测其 pid；不含活动功能的构建所对应的会话对 `list_peers` 可见，对快照则不可见。`doing` 取决于模型自己使用 `todo_write` 的习惯。
