# Agent Note: A shared provider cache-routing key for one delegation tree

Status: implemented

English | [中文](2026-09-27-delegation-tree-cache-key.zh.md)

## Problem

Each session in a delegation tree sent its own session id as the sole provider cache-routing signal. `dsh-llm-pi-ai` mapped that id onto pi-ai's session-scoped routing (a per-session WebSocket, the `session-id` header, and OpenAI's `prompt_cache_key`), and `dsh-llm-deepseek` mapped it onto an `x-deepseek-harness-session-id` header. OpenAI's own cache keys on the hash of a request's leading bytes plus this routing key, so sibling and fork children of the same parent — which share a common request prefix — never landed on the same cache entry: each child's first request paid full, uncached input cost. DeepSeek's cache is account-global and unaffected by session identity, so this cost was OpenAI-family-specific.

## Decision

`GenerateOptions` (`packages/llm/llm/src/types.ts`) gains `cacheKey?: Branded<'SessionId'>` — the same locally-declared brand `sessionId` already uses, because importing `dsh-session`'s `SessionId` would cycle — documented as the session id whose provider-side cached prefix a request shares. It is transport metadata and never model-visible, so the session log does not record it: the `request/header` event carries only `config`, `adapterDefaults`, and `tools`. The loop recomputes `cacheKey` for each request from the live session registry rather than reading it back from the log.

`dsh-session` exports `delegationTreeRoot(header, lookupHeader)` (`packages/core/session/src/delegation.ts`): the walk follows `parentSession` upward through headers `lookupHeader` can resolve, and returns the id of the first ancestor whose header does not resolve (already ended, or not currently loaded in this process — that id is known from the last resolvable header's own `parentSession` field even though the ancestor's own header could not be loaded), or the top-level ancestor's own id when every header up to it resolves. A disposed root therefore still keys the whole tree, because its child already knows its id; an unloaded intermediate ancestor instead keys only its own subtree, because the walk cannot see past it. The function takes a header and a lookup callback, never a live parent `Agent`, so it has no dependency on live in-process state beyond whatever `lookupHeader` itself consults. `dsh-agent-loop` (`agent.ts`) and `dsh-compaction-basic` (`summarizer.ts`) both stamp `cacheKey: delegationTreeRoot(session.header, id => ctx.sessions.get(id)?.header)` beside `sessionId` on every request; `ctx.sessions` is the live, in-process session registry, so this particular lookup only ever sees sessions currently loaded in this process, and the resolved root can therefore differ between two calls in the same session if an ancestor's liveness changes between them (see Consequences). `summarizeWithLlm` (`summarizer.ts:146-162`) sends `[...input.messages, COMPACTION_INSTRUCTION]` — that same session's own replayed conversation prefix (its `toolHistory` and `tools` included) plus one appended user message — so it must carry that session's own `cacheKey` to land on the same cached prefix as the session's ordinary requests (PR #10 measured 3200 cached tokens from exactly this reuse). Session-title generation keeps `sessionId` only and is deliberately not stamped: its request is a fixed instruction plus a JSON-framed dump of that session's own messages, an unrelated structure that shares no prefix with anything, so a shared key would have nothing to route onto.

`dsh-llm-pi-ai` (`adapter.ts`) exports `sharesPromptCacheKey(model)`, `overridePromptCacheKey(cacheKey)`, and `resolveCacheKeyOverride(options)`. `sharesPromptCacheKey` gates on pi-ai's own `openai` and `openai-codex` *provider ids* alone, never on the resolved route's host: pi-ai's real `openai-codex` provider (the ChatGPT/Codex sign-in route) resolves to `chatgpt.com/backend-api`, not `api.openai.com`, so a host clause silently excluded the harness's primary target route. `overridePromptCacheKey` builds the pi-ai `onPayload` hook `streamWithSnapshot` installs whenever `resolveCacheKeyOverride` finds a `cacheKey` distinct from the request's own `sessionId`; the hook replaces `payload.prompt_cache_key` only when the payload already carries a defined one. That "only replace, never add" rule is what makes one hook correct across pi-ai's different API modules without re-deriving their internal decisions: `cacheRetention: 'none'` omits the field on every module (`dist/api/openai-completions.js`, `openai-responses.js`, and `openai-codex-responses.js` each read it independently), `openai-completions` additionally omits it once its resolved host is not OpenAI's platform API, and this hook defers to whichever of those pi-ai already decided. In pi-ai 0.85.1 `dist/api/openai-codex-responses.js`, the hook runs on `body` (lines 171-175) before the single `JSON.stringify(body)` (line 179) that both its SSE and WebSocket transports send, so the override reaches either transport structurally; the WebSocket request id and the `session-id` header both keep using `codexSessionId` (the request's own session id), independent of the hook. `sessionId` itself is untouched everywhere: pi-ai's own per-session WebSocket routing and `session-id` header keep using the request's own id, so continuity and replay separation are unaffected. `dsh-llm-deepseek` ignores `cacheKey` entirely; DeepSeek's cache is account-global, so there is nothing session-scoped to route around.

## Alternatives considered

**Gate `sharesPromptCacheKey` on the resolved route's host.** An initial implementation additionally required `model.baseUrl.includes('api.openai.com')`. Rejected once measured against pi-ai's real provider table: `openai-codex` (ChatGPT sign-in, the target of the original measurement) resolves to `chatgpt.com/backend-api`, so the host clause made the override inert on exactly the route it was built for. Provider id alone is what pi-ai's own catalog fixes per route; host is not.

**Set the child's own `sessionId` to the delegation tree's root instead of adding `cacheKey`.** This would need no new field, but `sessionId` is also pi-ai's per-session WebSocket key, its `session-id` header, DeepSeek's session header, and the loop's own replay-cursor separator; collapsing every child in a tree onto one `sessionId` would merge those unrelated routing and replay concerns along with cache routing.

**Fail loud when an ancestor is unresolvable or the lineage cycles.** `delegationTreeRoot` is consulted on the hot request-assembly path for a value the design calls a routing hint, not a correctness-critical identity. A hard failure there would turn a caching optimization into an outage; falling back to the nearest known ancestor (or, for a cycle, the first ancestor id the walk reaches a second time) keeps every request routable.

**Derive the root from a live parent `Agent` object.** The loop only has the current session's own header and the live session registry at the point it assembles a request; a resumed child's parent may not be running in this process at all. `delegationTreeRoot` itself takes a header and a lookup callback instead, so it works the same way whether the caller's lookup happens to find a given ancestor live or not, without ever needing a live parent reference.

## Consequences

- Sibling and fork children of one delegation tree on the `openai`/`openai-codex` routes route to the same provider-side cached prefix instead of each starting a separate one under its own session id; DeepSeek and every other route are unaffected.
- `cacheKey` is derivable and testable from a header plus a lookup function alone (`packages/core/session/tests/delegation.spec.ts`), with no dependency on a live parent `Agent` object — but the loop still recomputes it per request from the live, in-process session registry, not from durable storage. While every ancestor stays live, the whole tree resolves to the same root id; once an intermediate ancestor is not live (disposed, or not loaded after a cold resume), the walk falls back to the nearest ancestor id it can still name. A session's own resolved key can therefore change between two of its own requests, and a cold-resumed child can land on a different key than a live sibling in the same tree.
- The harness proves its own assembled request options and the pi-ai wire body it produces; it does not prove a provider cache hit. Provider-side behavior remains outside what these tests can observe, matching the equivalent accepted risk in [the fork-children-stay-one-shot Agent Note](../architecture/2026-08-10-fork-children-stay-one-shot.md).
- A corrupted or cyclic header lineage degrades to the nearest known ancestor (or, for a cycle, the first ancestor id the walk reaches a second time) rather than failing the request; this is an accepted trade against treating a cache-routing hint as a hard invariant.
